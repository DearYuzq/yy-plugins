## 流程对比

| 特性 | /tdd-quick | /sdd-standard | /sdd-full |
|------|------------|---------------|-----------|
| 需求澄清 | ❌ 跳过 | ✅ 简单澄清 | ✅ 完整发散-收敛 |
| 规范文档 | 可选 | ✅ 必须 | ✅ 必须 |
| 实现计划 | ❌ 跳过 | ✅ 必须 | ✅ 必须 |
| 安全验证 | ❌ 跳过 | ⚠️ 基础 | ✅ 红蓝对抗 |
| 适用场景 | Bug修复、简单功能 | 新功能开发 | 复杂系统、安全敏感 |
| 预计耗时 | 30分钟-2小时 | 2-8小时 | 1-3天 |

## 示例场景

### 场景 1: 修复 Bug

```bash
/tdd-quick 修复 UserService 中邮箱验证的 bug

# 流程：
# 1. 理解问题 → 读取相关代码
# 2. 编写测试 → 重现 bug
# 3. 修复代码 → 使测试通过
# 4. 验证 → 确认修复
```

### 场景 2: 添加简单功能

```bash
/tdd-quick 为 User 实体添加 fullName 计算属性

# 流程：
# 1. 理解需求 → 确认字段组合方式
# 2. 编写测试 → 测试各种边界情况
# 3. 实现 → 添加计算属性
# 4. 验证 → 测试通过
```

### 场景 3: 开发中等复杂度功能

```bash
/sdd-standard 实现用户认证模块，支持注册、登录和 JWT token 管理

# 流程：
# 1. 简单澄清 → 确认认证方式
# 2. 规范 → 定义用户故事和验收标准
# 3. 计划 → 拆分实现步骤
# 4. 测试 → 编写测试用例
# 5. 实现 → 编写代码
# 6. 审查 → 代码审查
# 7. 验证 → 确认通过
```

### 场景 4: 开发复杂系统

```bash
/sdd-full 开发支付系统，支持微信支付、支付宝支付、退款和对账功能

# 流程：
# 1. 发散阶段：
#    - Preprocessor: 分析需求可信度
#    - Diverger: 探索各种支付方案
#    - Decomposer: 拆解需求树
#    - Challenger: 质疑不合理需求
#    【用户确认】
# 2. 收敛阶段：
#    - Completer: 补全边界情况
#    - Explorer: POC 技术验证
#    - Red-Teamer: 安全攻击测试
#    - Blue-Teamer: 防御方案设计
#    【最终评审】
# 3. SPEC → PLAN → TEST → IMPL → REVIEW → VERIFY
```

## 单独命令

如果需要单独执行某个阶段：

| 命令 | 用途 |
|------|------|
| `/clarify` | 启动多阶段需求澄清 |
| `/spec` | 创建功能规范文档 |
| `/plan` | 生成实现计划 |
| `/impl` | 执行实现 |
| `/review` | 代码审查 |
| `/verify` | 运行验证循环 |
| `/status` | 查看流程状态 |

## 最佳实践

1. **不要跳过必要的阶段**
   - 复杂功能必须走完整流程
   - 简单功能可以快速迭代

2. **善用 status 命令**
   ```bash
   /status  # 查看当前进度
   ```

3. **保存中间产物**
   - 规范、计划文档可以复用
   - 审查报告帮助后续改进

4. **团队协作**
   - 规范文档可以共享评审
   - 计划文档帮助分工

## 常见问题

**Q: 我不确定需求复杂度，该选哪个流程？**

A: 先尝试 `/sdd-standard`，如果在规范阶段发现需求不够清晰，可以切换到 `/sdd-full`。

**Q: 流程执行到一半可以暂停吗？**

A: 可以。使用 `/status` 查看当前进度，下次可以 `/impl --resume` 继续。

**Q: 测试一直不通过怎么办？**

A: 可能需要回退到计划阶段重新评估技术方案。
