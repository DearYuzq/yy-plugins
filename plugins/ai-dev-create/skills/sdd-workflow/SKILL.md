# SDD Workflow - 规范驱动开发

SDD (Specification-Driven Development) 是一种系统化的开发方法论，强调在编码前先定义清晰的规范。

## 激活时机

- 开发复杂的新功能
- 需要多人协作的模块
- 需要详细文档的功能
- 用户明确请求 SDD 流程

## 核心流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         SDD 完整流程（7 阶段）                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │

│  └─────────┘               └─────────┘              └──────┘          │
│       ▲                                                        │          │
│       │ 需求模糊                                                │          │
│       │                                                        ▼          │
│  ┌─────────┐                                           ┌──────────┐      │
│  │   END   │◀──────────────────────────────────────────│   PLAN   │      │
│  └─────────┘                                           └──────────┘      │
```

## 阶段详解

### Phase 0: CLARIFY（澄清）

**目标**：澄清模糊需求，确保需求理解一致

**触发条件**：清晰度评分 < 0.7

**输入**：用户需求描述

**输出**：
- 澄清文档 (`.claude/clarifications/{feature}-{session_id}.md`)
- 清晰度评分（目标 ≥ 0.8）
- 假设列表
- 用户确认记录

**退出条件**：
- 清晰度评分 ≥ 0.8
- 用户确认理解正确

### Phase 1: SPEC（规范）

**目标**：创建清晰的功能规范文档

**触发条件**：CLARIFY 完成 或 清晰度 ≥ 0.7

**输入**：需求 + 澄清文档（如有）

**输出**：
- 功能规范文档 (`.claude/specs/[feature].md`)
- 用户故事
- 验收标准

**规范模板**：

```markdown
# 功能规范：[功能名称]

## 概述
[2-3 句描述功能的目的和价值]

## 用户故事
As a [角色],
I want to [行为],
So that [价值/收益]

## 功能需求

### 核心功能
- [ ] FR-1: [功能描述]
- [ ] FR-2: [功能描述]

### 边界条件
- [ ] 输入验证：[规则]
- [ ] 错误处理：[策略]

## 非功能需求
- 性能：[具体指标]
- 安全：[具体要求]
- 可用性：[具体要求]

## 验收标准
- [ ] AC-1: [验收条件]
- [ ] AC-2: [验收条件]

## 技术约束
- 框架版本：[版本]
- 兼容性：[要求]
```

### Phase 2: PLAN（计划）

**目标**：生成详细的实现计划

**触发条件**：SPEC 用户确认

**输入**：规范 + 现有代码结构

**输出**：
- 实现计划文档 (`.claude/plans/[feature].md`)
- 文件变更清单
- 测试策略
- 风险评估结果

**计划模板**：

```markdown
# 实现计划：[功能名称]

## 架构变更
- 新增文件：[列表]
- 修改文件：[列表]
- 删除文件：[列表]

## 实现步骤

### Phase 1: [阶段名]
1. **[步骤]** (File: path/to/file)
   - Action: [具体操作]
   - Why: [原因]
   - Dependencies: [依赖]
   - Risk: Low/Medium/High

### Phase 2: [阶段名]
...

## 测试策略
- 单元测试：[范围]
- 集成测试：[范围]
- E2E 测试：[用户旅程]

## 风险评估
| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| [风险] | [影响] | [措施] |
```

### Phase 3: TEST（测试）

**目标**：编写全面的测试用例

**触发条件**：PLAN 风险通过

**输入**：计划 + 规范

**输出**：
- 单元测试文件
- 集成测试文件
- E2E 测试文件

**完成条件**：
- 测试可运行（RED 状态）
- 测试覆盖率目标已设定

**TDD 循环**：

1. 编写失败的测试
2. 运行测试（RED）
3. 编写最小实现
4. 运行测试（GREEN）
5. 重构代码
6. 运行测试（仍然 GREEN）

### Phase 4: IMPL（实现）

**目标**：编写生产代码使测试通过

**触发条件**：TEST 完成（RED 状态）

**输入**：测试用例 + 实现计划

**输出**：
- 生产代码
- 文档更新（如适用）

**完成条件**：
- 所有测试通过（GREEN 状态）
- 无编译/构建错误

**实现原则**：
- 最小实现原则
- 不可变性优先
- 单一职责
- 代码可读性

### Phase 5: REVIEW（审查）

**目标**：检查代码质量、安全性和可维护性

**触发条件**：IMPL 完成（GREEN 状态）

**输入**：代码变更 + 测试运行结果

**输出**：
- 审查报告 (`reviews/[feature]-review.md`)
- 问题分类（CRITICAL/HIGH/MEDIUM/LOW）
- 改进建议

**审查维度**：
- 代码质量：结构、可读性、命名
- 安全性：漏洞、注入、权限
- 性能：N+1 查询、缓存、资源
- 可维护性：依赖、错误处理、日志

**退出条件**：
- 无 CRITICAL 问题
- 无 HIGH 问题（或已修复）

### Phase 6: VERIFY（验证）

**目标**：全面验证实现质量

**触发条件**：REVIEW 通过

**输入**：所有产出物（规范、计划、测试、代码、审查报告）

**输出**：
- 验证报告
- 问题清单（如有）
- 完成确认

**验证维度**：
- 功能验证：所有验收标准通过
- 测试验证：覆盖率 ≥ 80%
- 代码验证：无 CRITICAL/HIGH 问题
- 安全验证：无已知漏洞
- 性能验证：满足非功能需求

## 命令集成

| 阶段 | 命令 | 说明 |
|------|------|------|
| CLARIFY | `/clarify` | 澄清模糊需求 |
| SPEC | `/spec` | 创建功能规范 |
| PLAN | `/plan` | 生成实现计划 |
| TEST | `/test` | 编写测试用例 |
| IMPL | `/impl` | 执行实现 |
| REVIEW | `/review` | 代码审查 |
| VERIFY | `/verify` | 运行验证循环 |

## 最佳实践

1. **规范先行**：不要跳过 SPEC 阶段
2. **增量迭代**：每个阶段独立可验证
3. **持续验证**：每完成一个步骤就验证
4. **文档同步**：保持文档与代码一致
5. **回溯机制**：失败时回到相应阶段

## 与 TDD 的关系

SDD 包含 TDD：
- CLARIFY 阶段确保需求清晰
- SDD 在 PLAN 阶段确定架构
- TEST 阶段执行 TDD 流程
- REVIEW 阶段确保代码质量
- VERIFY 阶段验证整体质量

```
SDD:  CLARIFY → SPEC → PLAN → TEST → IMPL → REVIEW → VERIFY
                            ↓
TDD:                  RED → GREEN → REFACTOR
```
