# Clarification Workflow - 多阶段需求澄清

## 激活时机

- 用户运行 `/clarify` 命令
- 用户请求澄清需求
- SDD 流程需要澄清阶段

---

## 核心理念

**发散→收敛**：先探索各种可能性，再收敛到高质量需求。

**核心假设**：用户可能说不清、说不全、隐瞒、撒谎。系统需要主动发现问题并引导澄清。

---

## Agent 职责速查

| Agent | 职责 | 核心方法 |
|-------|------|----------|
| preprocessor | 预处理：质疑用户输入 | 完整性检查、一致性检查、可行性质疑 |
| diverger | 畅想：探索可能性空间 | MECE分解、类比启发、What-If分析 |
| decomposer | 拆解：构建需求树 | 需求分类、依赖分析、MoSCoW优先级 |
| challenger | 挑刺：正交过滤 | SMART验证、ROI分析、方法论判定 |
| completer | 补全：端到端完整性 | 旅程追踪、依赖链检查、缺失识别 |
| explorer | 探测：技术验证 | POC设计、验证代码生成、风险验证 |
| red-teamer | 红方：边界攻击 | 安全攻击、边界攻击、业务逻辑攻击 |
| blue-teamer | 蓝方：防御方案 | 攻击评估、解决方案设计、成本分析 |

## 关键确认点

### 用户确认点（发散阶段后）

```markdown
## 发散阶段完成

### 摘要
- 原始需求：{count} 个
- 发散后需求：{count} 个
- 过滤后需求：{count} 个

### 待决策冲突
| 冲突ID | 描述 | 需求A | 需求B |
|--------|------|-------|-------|
| C-001 | {描述} | FR-002 | FR-003 |

### 是否进入收敛阶段？

选项：
A) 确认，进入收敛阶段
B) 需要修改发散结果
C) 查看详细报告
```

### 最终评审（收敛阶段后）

```markdown
## 收敛阶段完成

### 最终需求汇总
- 功能需求：{count} 个
- 非功能需求：{count} 个
- 安全需求：{count} 个
- 约束需求：{count} 个

### 质量评分
| 维度 | 评分 |
|------|------|
| 完整性 | {score}/10 |
| 可行性 | {score}/10 |
| 安全性 | {score}/10 |

### 是否通过最终评审？

选项：
A) 通过，生成最终需求文档
B) 需要修改
C) 查看详细报告
```

## 失败恢复

| 失败阶段 | 恢复策略 |
|----------|----------|
| 可信度过低 | 解决阻塞性问题后重新预处理 |
| 发散评分过低 | 增加参考产品，重新发散 |
| 用户拒绝确认 | 返回 Challenger 修改 |
| POC 验证失败 | 修改需求或新增需求 |
| CRITICAL 漏洞 | 必须修复后继续 |
| 最终评审不通过 | 返回对应阶段修改 |

---

## 最佳实践

1. **不要跳过发散阶段**：发散阶段是发现需求盲区的关键
2. **用户确认是必须的**：发散→收敛的确认点不可跳过
3. **POC 自动执行**：探测阶段的验证代码会自动执行
4. **红蓝顺序执行**：先红方攻击，后蓝方防御
5. **闭环机制**：遇到问题可返回早期阶段修改
